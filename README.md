# Partizan Telegram Bot

Небольшой сервер доставки уведомлений о контроле присутствия для Partizan.
Основной запуск — **Docker Compose**. В контейнере Python 3.13 и `requests[socks]` для HTTP/SOCKS-прокси; зависимости устанавливаются при сборке образа. Отдельный сервер базы данных не нужен. Также сохранён запуск напрямую Python 3.10+.

## Готовый образ: Portainer, Throne и автоматические обновления

Образ: **`ghcr.io/narvik6/partizan-telegram-bot:latest`**, архитектуры `linux/amd64` и `linux/arm64`.
Для сервера с Portainer используйте [compose.portainer.yaml](compose.portainer.yaml): в нём нет `build`, исходники и Python на сервере не нужны.

1. В Portainer создайте stack из `compose.portainer.yaml` (через Git repository или вставив содержимое).
2. В переменных stack задайте `BOT_TOKEN` из BotFather. Токен остаётся на сервере, в GitHub Secrets его добавлять не нужно.
3. На сервере должны существовать Docker-сети **`vpn`** и **`proxy`**. Throne подключён к `vpn` и доступен по имени **`throne`** на SOCKS-порту **2080**; Nginx Proxy Manager подключён к `proxy`. Бот подключается к обеим сетям.
4. `TELEGRAM_PROXY` по умолчанию — `socks5h://throne:2080`. `socks5h` передаёт DNS-разрешение прокси. Если у Throne HTTP-порт, укажите `http://throne:ПОРТ`. Для запуска без прокси используйте обычный `compose.yaml`.
5. Разверните stack. В Nginx Proxy Manager укажите схему `http`, целевой хост `partizan-telegram-bot`, порт `8787`; соединение идёт по сети `proxy`. Для поддомена настройте DNS и SSL-сертификат с принудительным HTTPS. Проверка: `https://ваш-поддомен/health` возвращает `{"ok":true}`. API также публикуется на хосте только как `127.0.0.1:8787`, что позволяет использовать SSH-туннель, как описано ниже.
6. Создайте webhook обновления stack в Portainer. Его HTTPS-адрес добавьте в репозитории GitHub: **Settings → Secrets and variables → Actions → New repository secret → `PORTAINER_WEBHOOK_URL`**. Адрес не публикуйте: он разрешает запуск обновления.

Workflow [docker.yaml](.github/workflows/docker.yaml) выполняется при push в `main` и вручную из Actions:

```text
тесты → сборка amd64/arm64 → публикация GHCR → POST webhook Portainer
```

Pull request запускает только тесты, без публикации и обновления сервера. Без секрета образ публикуется, webhook пропускается. Для GHCR используется встроенный `GITHUB_TOKEN`, отдельный токен публикации не нужен. Теги: `latest` и `sha-<полный commit>` для возврата к конкретной версии.

Первый образ уже опубликован, анонимное получение manifest для amd64/arm64 проверено. Серверу вход в GHCR не нужен. При публикации нового package или форка отдельно проверьте его видимость: **Packages → package → Package settings → Change visibility → Public**. Публичность репозитория сама по себе не подтверждает публичность образа.

Portainer должен скачивать новый образ при redeploy (`pullimage=false` в webhook использовать нельзя). Ответ webhook означает принятие запроса: окончательное состояние контейнера смотрите в Portainer. Состояние SQLite остаётся в volume того же stack; не удаляйте volume при обновлении. Запускайте одну копию бота с этим токеном.

В документации Portainer stack webhook относится к Business Edition. Если друг уже использует подходящий webhook, менять его схему не требуется. Без доступного webhook можно обновлять вручную: `docker compose -f compose.portainer.yaml pull` и затем `docker compose -f compose.portainer.yaml up -d` с переменными stack в окружении.

[Публикация образов GitHub Actions](https://docs.github.com/en/actions/tutorials/publish-packages/publish-docker-images) · [Portainer stack webhooks](https://docs.portainer.io/user/docker/stacks/webhooks)

## Прокси

`TELEGRAM_PROXY` задаёт прокси только для запросов к Telegram и имеет приоритет. Поддерживаются `http://`, `https://`, `socks5://`, `socks5h://`. Если он не задан, библиотека учитывает стандартные `HTTPS_PROXY`, `HTTP_PROXY`, `ALL_PROXY`, `NO_PROXY` (и варианты в нижнем регистре). Поэтому вариант друга с `ALL_PROXY=socks5://throne:2080` также поддерживается при отсутствии `TELEGRAM_PROXY`.

Все обращения Telegram — проверка токена, long polling, администраторы и отправка сообщений — проходят через один настроенный маршрут. Ошибки не печатают токен или пароль прокси. При недоступности явно заданного прокси обхода напрямую нет. Локальный входящий API Partizan через него не отправляется.

[Requests: HTTP/SOCKS-прокси](https://requests.readthedocs.io/en/stable/user/advanced/#proxies)

## Запуск в Docker

```bash
git clone https://github.com/narvik6/partizan-telegram-bot.git
cd partizan-telegram-bot
cp .env.example .env
chmod 600 .env
```

Создайте бота у [@BotFather](https://t.me/BotFather) командой `/newbot` и внесите выданный токен в `.env`:

```dotenv
BOT_TOKEN=ваш_токен
```

```bash
docker compose up -d --build
docker compose logs -f bot
```

Для запуска на сервере нужны Docker Engine и Compose plugin. Токен передаётся из `.env` при запуске, в образ не копируется. Контейнер работает от непривилегированного пользователя, API доступен на хосте через `127.0.0.1:8787`.

Состояние находится в постоянном Docker volume `bot-data` (`/data` внутри контейнера). Обновление не сбрасывает получателей и коды:

```bash
git pull
docker compose up -d --build
```

Остановить: `docker compose down`. Сам volume при этом сохраняется. Удаление volume удалит подписки и коды подключения.
Выход из просмотра логов через Ctrl+C контейнер не останавливает.

Бот получает команды через long polling; Telegram webhook не нужен. Существующий webhook автоматически не удаляется. Запускайте одну копию с одним токеном.

### Запуск без Docker

При установленном Python 3.10+ тот же `.env` можно использовать напрямую:

```bash
python3 bot.py
```

Перед первым прямым запуском создайте виртуальное окружение и установите зависимости: `python3 -m venv .venv`, `. .venv/bin/activate`, `python -m pip install -r requirements.txt`.

При прямом запуске Ctrl+C завершает бота; `.env` получает права 0600 на Unix, состояние по умолчанию хранится в `data/bot.sqlite3`.

## Личный чат

1. Откройте своего бота в Telegram и нажмите `/start`.
2. Бот пришлёт **код подключения** этого личного чата.
3. В Partizan откройте настройки уведомлений → Telegram, укажите адрес сервера бота и этот код.
4. Включите Telegram и событие «Контроль присутствия», нажмите проверку Telegram.

## Группа

1. Администратор группы сначала открывает личный чат с ботом и нажимает `/start`.
2. Добавляет бота в группу с разрешением отправлять сообщения.
3. В группе вводит `/connect` или `/connect@ИмяВашегоБота`.
4. Бот отправит **код группы администратору в личный чат**. Укажите его в Partizan вместо кода личного чата.

Код группы в общий чат не публикуется. Подключать/отключать группу могут её администраторы.
Настраивать боту чтение всех сообщений или отключать privacy mode не требуется: используются явные команды.
Команда `/stop` в соответствующем чате отключает доставку. `/connect` включает её снова.

Один код связан с одним получателем. Для отправки в другой чат нужен его собственный код.
Код подключения позволяет отправлять уведомления в этот чат; не публикуйте его. Токен BotFather приложению Partizan не передаётся.

## Подключение к серверу

По умолчанию API слушает **127.0.0.1:8787**. Если бот и Partizan на одном компьютере,
адрес в приложении: `http://127.0.0.1:8787`.

Для удалённого сервера самый простой вариант без домена — SSH-туннель на компьютере с Partizan:

```bash
ssh -N -L 8787:127.0.0.1:8787 user@server
```

В приложении остаётся `http://127.0.0.1:8787`. На сервере достаточно запуска через Compose с одним токеном в `.env`.
Другой вариант — разместить этот локальный API за вашим HTTPS reverse proxy и указать его HTTPS-адрес в приложении.
Туннель или прокси обеспечивают доступ компьютера к серверу; один запуск интерпретатора сам по себе сетевую маршрутизацию не настраивает.

Дополнительные необязательные переменные: `HTTP_HOST`, `HTTP_PORT`, `STATE_FILE` (см. `.env.example`).
Без необходимости не публикуйте незашифрованный HTTP API в интернете.

## Что отправляется

Бот доставляет только событие обнаружения контроля посещения и явную проверку связи.
Присутствие не подтверждает, QR не сканирует, учётные данные СДО/Pulse и почтовые 2FA-коды не получает.
Partizan передаёт заголовок и текст уведомления; QR-токен и полный адрес вебинара не передаются.
Управления компьютером, рассылки всем пользователям и команд отметки нет.

Регистрации чатов, коды подключения, позиция long polling и недавние ID доставленных событий
хранятся в SQLite: `/data/bot.sqlite3` в Docker volume либо `data/bot.sqlite3` при прямом запуске. SQLite и `.env` исключены из Git. Сохраняйте volume/каталог состояния при обновлении:
он нужен для действующих подключений и подавления повторов после перезапуска.
Доставка при сетевом обрыве не гарантирует «ровно один раз»: Telegram не предоставляет идемпотентный sendMessage.

## API для приложения

`POST /v1/attendance`, `Authorization: Bearer <код подключения>`, `Content-Type: application/json`:

```json
{
  "event_id": "unique-event-id",
  "kind": "attendance_required",
  "title": "Контроль присутствия",
  "body": "На вебинаре появился QR-код Pulse."
}
```

Для явной проверки связи `kind` равен `test`. Получателя нельзя переопределить в запросе.
HTTP 200 и `{"ok":true}` подтверждают доставку либо уже доставленный повтор этого ID.
401 — неверный код, 410 — чат отключён, 502 — Telegram не подтвердил доставку.
`GET /health` проверяет доступность HTTP-процесса, без отправки сообщения.

## Проверки

```bash
docker build --target test -t partizan-telegram-bot:test .
docker run --rm --network none --read-only --tmpfs /tmp:size=16m partizan-telegram-bot:test
```

Либо без Docker после установки `requirements.txt`: `python3 -m unittest -v`.

Проверяются регистрация личного чата/группы, права администратора, сохранение состояния,
настоящие локальные HTTP-запросы, ограничение получателя, ошибки доставки и дедупликация.
Дополнительно проверяется реальный локальный HTTP-прокси, HTTPS CONNECT, SOCKS5 с передачей имени хоста прокси, приоритет настроек и сохранение Telegram retry_after. Тесты не обращаются в Telegram и никому не отправляют сообщения.

Протокол Telegram: [официальный Bot API](https://core.telegram.org/bots/api).
